# Деплой и задачи Celery

Workflow `.github/workflows/deploy.yml` запускается при push в main. Он
проверяет скрипты, берёт `/run/lock/metateks-deploy.lock`, загружает main и
применяет именно SHA запустившего его коммита через `merge --ff-only`.
GitHub concurrency не отменяет уже выполняющийся деплой новым push.

`scripts/deploy.sh` вызывается workflow под этой блокировкой:

1. Проверяет свободное место (минимум 3072 МБ) и собирает web/celery, пока
   старые контейнеры продолжают работать.
2. Определяет ID текущего контейнера Celery. `celery_deploy_guard.py`
   запрашивает ответы именно его воркера; отсутствие, ошибка или неверная
   структура ответа останавливают выкатку.
3. Сохраняет исходный список очередей внутри старого контейнера в
   `/tmp/metateks-deploy-consumers.json` (права 600), затем вызывает
   `cancel_consumer` для каждой очереди и проверяет фактическую паузу.
4. Ждёт опустошения `reserved`, `scheduled` и `active` до 40 минут. Требует
   два последовательных пустых снимка. Новые задания остаются в Redis;
   уже принятые воркером задания завершаются.
5. Поднимает только web, где entrypoint выполняет миграции. Пока `/health/`
   не вернёт успех, старый Celery остаётся живым с приостановленным приёмом.
6. Обновляет Celery и проверяет ответы нового воркера и наличие потребителей
   очередей. Если контейнер остался прежним, возвращает ему исходные очереди.
7. Применяет изменения nginx и перечитывает его конфигурацию с новым адресом
   web через reload. PostgreSQL и Redis этот скрипт не пересоздаёт.

Если ожидание или обновление web завершается ошибкой, обработчик выхода
возвращает исходному работающему воркеру его очереди. Очереди не очищаются,
задачи не отзываются, активные задания не завершаются принудительно.

Механизм использует штатные [команды управления очередями Celery](https://docs.celeryq.dev/en/v5.5.3/userguide/workers.html#queues-canceling-consumers).
Он проверен с установленным на проде Celery 5.4.0. Ожидание относится к задачам
Celery; краткий разрыв HTTP-запросов при пересоздании web по-прежнему возможен.

## Восстановление при ошибке

Обычно `resume` выполняется автоматически. Если в логе есть `RESUME FAILED`
или SSH/процесс деплоя был оборван без выполнения обработчика выхода,
использовать **ID старого контейнера из лога**, а не выбирать новый наугад:

```bash
cd /opt/metatecks
old_worker=ID_ИЗ_СТРОКИ_Draining_old_celery_container
docker exec -i "$old_worker" python - resume < scripts/celery_deploy_guard.py
```

Команда восстанавливает сохранённые очереди и проверяет подтверждение. При
ошибке файл состояния остаётся для повторной попытки. Если старый контейнер
уже удалён, проверить новый воркер и причину сбоя по логу workflow. Скрипт
не откатывает миграции или образы автоматически.

## Проверки

Без Docker и брокера:

```bash
python3 scripts/test_celery_deploy_guard.py
python3 scripts/test_deploy.py
bash -n scripts/deploy.sh
```

Эти проверки также выполняются в GitHub Actions до подключения к серверу.
Они проверяют отсутствующие и некорректные ответы, подтверждения паузы,
ожидание всех трёх типов заданий, таймаут, прерывание, восстановление очередей,
ошибки сборки/web/healthcheck/Celery и порядок обновления сервисов.

Интеграционная проверка `test_celery_deploy_guard_integration.py` запускается
только в отдельном контейнере приложения, с `PROBE_QUEUE=deployguard-probe-...`,
`PYTHONPATH=/app`, лимитом 512 МБ и 1 CPU. Сначала этот файл запускается с
аргументом `worker`, затем исполняется без аргументов в том же контейнере.
Перед изменением потребителей тест проверяет, что воркер слушает только
указанную тестовую очередь. Рабочая очередь 1С не используется.
