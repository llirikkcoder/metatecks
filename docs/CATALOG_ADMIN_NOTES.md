# Каталог: как устроены сортировка и вывод характеристик

Документ отвечает на вопросы, которые регулярно задаёт администратор магазина,
и фиксирует неочевидные места, о которые уже спотыкались. Актуально на 11.09.2026.

---

## Сортировка товаров

### Как товары сортируются на сайте

Единая точка — `get_shown_products()` в `apps/catalog/models/categories.py`:

```python
# с выбранным городом
.order_by('-city_stock_sort', '-is_in_stock', 'order')
# без города
.order_by('-is_in_stock', 'order')
```

То есть **ручной порядок (`order`) применяется только внутри групп «в наличии» /
«нет в наличии»**. Товар без остатков не поднимется выше товаров в наличии, как бы
его ни перетаскивали в админке. Это не баг, а заложенная логика — но администратор
воспринимает это как «сортировка не работает», поэтому объяснять приходится каждый раз.

### Грабли: перетаскивание писало не в то поле

`SortableAdminMixin` из django-admin-sortable2 определяет поле сортировки как первый
элемент `ModelAdmin.ordering`, а при его отсутствии — `Meta.ordering[0]`.
У `Product` это `-is_in_stock` (булев флаг наличия), а не `order`.

Последствия до исправления:

- перетаскивание на позицию 2 и дальше → в `is_in_stock` писалось число ≥2 →
  `BooleanField.to_python` бросал `ValidationError` → ответ 400, строка возвращалась
  на место (администратор видел «ничего не происходит»);
- перетаскивание на позицию 0/1 → проходило и **переключало флаг «Есть на складе?»**,
  то есть портило данные о наличии;
- колонка `is_in_stock` в списке товаров подменялась ручкой перетаскивания.

Исправлено в коммите `22fbea3` одной строкой:

```python
class ProductAdmin(...):
    ordering = ['order']
```

**Не удаляйте эту строку.** Альтернатива — убрать `-is_in_stock` из
`Product.Meta.ordering`, но тогда нужно проверить все места, где сортировка
полагается на `Meta` неявно.

Испорченные записи на проде проверялись запросом (расхождение `is_in_stock` и
`number_in_stock`) — не найдено.

### Товары из 1С приходят без порядка

`sync_products()` не пишет поле `order` (см. `product_kw` в
`apps/third_party/cml/sync.py`), поэтому у всех импортированных товаров `order = 1`.
При равных ключах сортировки PostgreSQL возвращает произвольный порядок.
Осмысленную последовательность в подкатегории нужно один раз выставить руками —
дальше она сохраняется, обмен её не затирает.

## Порядок характеристик

### Порядок глобальный, и этого достаточно

Порядок задаётся полем `Attribute.order` (`Meta.ordering = ['order']`) и действует
для всего сайта. **Индивидуального порядка для модели, товара или категории нет.**

Технически в `SubCategory` есть три `SortedManyToManyField` со своей сортировкой
(`attributes`, `attributes_in_products`, `attributes_in_filter`), но из админки они
убраны (`apps/catalog/admin/categories.py`, fieldsets), а в выводе карточки не
участвуют — рабочим остаётся только глобальный `Attribute.order`.

Почему глобального порядка хватает (аргумент для разговора с клиентом):

- характеристик в справочнике 161, а в карточке выводятся только заполненные
  у модели — в среднем 9.8, максимум 16;
- характеристики разных типов техники не пересекаются («диаметр щетины» и
  «глубина копания» не встретятся в одной карточке);
- значит, важен только относительный порядок внутри набора, и достаточно, чтобы
  каждая характеристика попала в правильную «полосу» общего списка.

Рекомендованная схема полос (сверху вниз):

1. рабочие параметры (объём ковша, ширина захвата, глубина копания);
2. требования к технике и гидравлика (поток, давление, класс каретки);
3. собственные размеры изделия;
4. транспортные габариты и вес — в самом низу.

### Что проверено на живых карточках (11.09.2026)

Порядок уже наполовину соответствует схеме. Траншеекопатель TR_SS-1500-150K —
корректный порядок целиком. У щётки коммунальной «Ширина (мм)» выпадает из своей
группы и оказывается после гидравлики. Транспортные габариты идут
Высота → Длина → Ширина вместо привычного Д-Ш-В.

### Дубли характеристик в справочнике

Из 1С пришли пары характеристик, различающиеся только написанием единицы:

| Вариант 1 | Вариант 2 |
|---|---|
| Ширина | Ширина (мм) |
| Грузоподъемность (две записи) | Грузоподъемность (кг) |
| Диаметр щетины | Диаметр щетины (мм) |
| Угол поворота | Угол поворота (град.) |
| Номинальный гидравлический поток | Номинальный гидравлический поток (л/мин) |
| Объем по SAE | Объем по SAE (л) |

Последствия: в карточке могут оказаться две похожие строки, а фильтр по
характеристике делит технику на две части. Сортировкой не лечится — нужно сводить
к одному варианту, **и делать это на стороне 1С**, иначе следующий обмен создаст
дубли заново (новые атрибуты заводятся в `sync_properties()` по данным выгрузки).

### Как переставлять

Каталог → Характеристики. Все 161 помещаются на одной странице
(`list_per_page = 200`), пагинация не мешает. Перетаскивание за ручку слева,
сохранение происходит сразу AJAX-запросом, отдельной кнопки нет.
Здесь `SortableAdminMixin` работает корректно: у `Attribute`
`Meta.ordering = ['order']`.

## Почему характеристика не выводится в карточке

Значения хранятся в JSON `ProductModel.attrs` в виде `{"a<id>": value}`.
Сборка списка — `get_attrs_list_v3()` в `apps/catalog/models/products.py`.
Причины, по которым заполненная характеристика не появится на странице:

1. **Значение заполнено у `Product`, а не у `ProductModel`** — вывод идёт от модели.
2. **Falsy-значение отбрасывается**: `if not value: continue`. Ноль, пустая строка
   и `False` пропадают молча — самая частая причина «характеристика есть, а её нет».
3. Ключа нет в `attrs` либо атрибут удалён из справочника.
4. Для атрибутов «с вариантами» значение должно совпасть с id варианта; если 1С
   прислала строку вместо id, значение теряется.
5. **`dont_show_in_lists`** скрывает характеристику в плитке каталога, но не в карточке.
6. **Четыре характеристики намеренно исключены из таблицы** и выводятся отдельными
   блоками (`apps/catalog/views/product.py`): «Назначение», «Особенности конструкции»,
   «Опции в базовой комплектации» и «Срок изготовления».
   Сопоставление идёт **по точному тексту названия** — переименуете характеристику
   в справочнике, и блок на странице исчезнет.
7. Два атрибута с одинаковым `name` схлопнутся: словарь в карточке строится по имени.

### «Срок изготовления» — частый вопрос

Выводится не в таблице характеристик, а в блоке складов: «под заказ (21 раб. дней)»
для складов без остатка. Для складов с остатком вместо срока показывается количество.
Шаблон — `templates/product.html`, переменная `making_days`.

### Числа из 1С

Приходят дробными (`1500.0`), из-за чего на сайте выводилось «1500,0 мм» и
«под заказ (21,0 раб.дней)». Нормализуются функцией `_clean_attr_value()` в
`apps/catalog/models/products.py` (целые float приводятся к int).

⚠️ В файле **три** почти одинаковых метода — `get_attrs_list`, `get_attrs_list_v2`
и `get_attrs_list_v3` — с идентичными блоками формирования результата. Рабочий
только `v3`; правка, внесённая «по первому совпадению», попадает в `v2` и не даёт
эффекта (наступали на это в коммитах `dcb55a2` → `15d7944`). При правках проверяйте,
в какой именно метод вносите изменение.

## Массовое отключение товаров

В списке товаров есть действия `make_visible` / `make_hidden`
(`apps/catalog/admin/products.py`), меняющие поле `is_shown`:
отметить галочками → «Действие» → «Отключить отображение» → «Выполнить».
Заходить в карточки не нужно. `list_editable` для `is_shown` не подключён.

Массово гасит товары и синхронизация: при **полном** обмене товары, пропавшие
из 1С, получают `is_shown = False`.

## Характеристика в фильтре каталога

Флага «участвует в фильтре» у самой характеристики нет. Фильтр задаётся со стороны
подкатегории полем `SubCategory.attribute_in_filter` (одна характеристика на
подкатегорию):

- Каталог → Подкатегории → колонка «Характеристика в фильтре» (`list_editable`,
  правится прямо в списке, затем «Сохранить» внизу);
- либо карточка подкатегории → вкладка «Характеристики».

Выпадающий список сужается дважды: `limit_choices_to={'is_synced_with_1c': True}`
(характеристику не из 1С выбрать нельзя) и `SubCategoryAdminForm` оставляет только
те, что реально заполнены у моделей этой подкатегории.
