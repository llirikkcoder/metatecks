# Feature Specification: Исправление ошибок развертывания Docker

**Feature Branch**: `002-fix-docker-deployment`
**Created**: 2026-01-14
**Status**: Draft
**Input**: User description: "Исправление ошибок развертывания Docker - устранение SIGBUS ошибок при сборке и IntegrityError при миграциях PostgreSQL"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Надежный запуск Docker окружения (Priority: P1)

Как **разработчик**, я хочу **запустить проект через docker-compose без ошибок**, чтобы **иметь стабильное окружение для разработки и тестирования**.

**Why this priority**: Это критическая функциональность - без возможности запустить Docker окружение разработчики не могут работать с проектом в контейнеризованном виде, что блокирует тестирование и деплой.

**Independent Test**: Можно протестировать независимо выполнив `docker-compose up -d` и проверив, что все контейнеры запущены и имеют статус "healthy" без ошибок в логах.

**Acceptance Scenarios**:

1. **Given** чистая установка проекта с существующими Docker volumes, **When** выполняется `docker-compose up -d`, **Then** все контейнеры (db, redis, web, celery, nginx) запускаются успешно и переходят в статус "healthy"
2. **Given** запущенные контейнеры, **When** выполняется `docker-compose down && docker-compose up -d`, **Then** контейнеры перезапускаются без ошибок IntegrityError в логах
3. **Given** WSL окружение на Windows, **When** выполняется сборка Docker образа, **Then** сборка завершается без SIGBUS ошибок

---

### User Story 2 - Стабильные миграции базы данных (Priority: P2)

Как **DevOps инженер**, я хочу **применять миграции PostgreSQL идемпотентно**, чтобы **избежать конфликтов типов при повторных запусках и обновлениях**.

**Why this priority**: Стабильные миграции критичны для CI/CD pipeline и production деплоя. Без этого каждое обновление может вызывать непредсказуемые ошибки.

**Independent Test**: Можно протестировать независимо запустив миграции дважды подряд и убедившись, что не возникает ошибок "duplicate key value violates unique constraint".

**Acceptance Scenarios**:

1. **Given** существующая база данных с enum типами, **When** применяются новые миграции, **Then** enum типы обновляются без конфликтов и дублирования
2. **Given** база данных с уже примененными миграциями, **When** миграции запускаются повторно, **Then** Django корректно определяет что миграции уже применены и не пытается создать дубликаты
3. **Given** проблемный enum тип orders_deliverycompany, **When** применяются миграции, **Then** не возникает IntegrityError с constraint "pg_type_typname_nsp_index"

---

### User Story 3 - Оптимизированная сборка для WSL (Priority: P3)

Как **разработчик на Windows с WSL**, я хочу **собирать Docker образы без SIGBUS ошибок**, чтобы **работать в привычном WSL окружении без переключения на нативный Linux**.

**Why this priority**: Многие разработчики используют WSL для работы. Поддержка этого окружения улучшает developer experience, хотя проект может работать и на других платформах.

**Independent Test**: Можно протестировать независимо выполнив `docker-compose build` в WSL окружении и убедившись, что сборка завершается успешно.

**Acceptance Scenarios**:

1. **Given** WSL2 окружение на Windows, **When** выполняется `docker-compose build`, **Then** сборка образа завершается без fatal error SIGBUS
2. **Given** ограничения памяти/диска в WSL, **When** идет сборка больших образов, **Then** используются оптимизации (multi-stage build, кэширование слоев) для снижения нагрузки
3. **Given** успешная сборка образа, **When** образ запускается, **Then** все зависимости установлены корректно

---

### User Story 4 - Улучшенные health checks и зависимости (Priority: P3)

Как **системный администратор**, я хочу **иметь надежные health checks для всех сервисов**, чтобы **контейнеры запускались в правильном порядке и system был готов к работе**.

**Why this priority**: Правильный порядок запуска и health checks обеспечивают стабильность системы, но это вторично по сравнению с базовой работоспособностью.

**Independent Test**: Можно протестировать независимо проверив `docker ps` и `docker inspect` для каждого контейнера и убедившись, что health status корректен.

**Acceptance Scenarios**:

1. **Given** контейнер web зависит от db и redis, **When** выполняется docker-compose up, **Then** web контейнер ждет готовности db и redis перед запуском Django
2. **Given** PostgreSQL контейнер запускается, **When** health check проверяет готовность, **Then** check учитывает не только доступность порта, но и готовность принимать подключения
3. **Given** все контейнеры запущены, **When** проверяется их статус через docker-compose ps, **Then** все сервисы показывают "healthy" или "running"

---

### Edge Cases

- **Что происходит при полном удалении volumes?** При `docker-compose down -v` и последующем `docker-compose up -d` должна создаться новая чистая база с применением всех миграций без ошибок
- **Как система обрабатывает прерывание сборки?** Если сборка Docker образа прервана (Ctrl+C или ошибка), следующий запуск должен корректно продолжить с использованием кэша слоев
- **Что если миграция изменяет существующий enum?** Django миграции должны корректно обрабатывать изменения enum типов (добавление/удаление значений) без нарушения constraint
- **Как ведет себя система при нехватке памяти в WSL?** Docker должен выдавать понятное сообщение об ошибке вместо SIGBUS, с рекомендациями по увеличению лимитов

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА успешно запускать все Docker контейнеры (db, redis, web, celery, nginx) через `docker-compose up -d` без ошибок
- **FR-002**: Миграции PostgreSQL ДОЛЖНЫ применяться идемпотентно - повторный запуск не должен вызывать ошибок
- **FR-003**: Enum типы в PostgreSQL НЕ ДОЛЖНЫ создавать дубликаты, вызывающие IntegrityError с constraint "pg_type_typname_nsp_index"
- **FR-004**: Docker образы ДОЛЖНЫ собираться в WSL окружении без SIGBUS ошибок (fatal error: fault signal SIGBUS)
- **FR-005**: Контейнер web ДОЛЖЕН ждать полной готовности PostgreSQL и Redis перед запуском Django приложения
- **FR-006**: Health checks ДОЛЖНЫ корректно определять готовность каждого сервиса (db, redis, web, celery, nginx)
- **FR-007**: Система ДОЛЖНА корректно обрабатывать миграции с изменением enum типов без конфликтов
- **FR-008**: При возникновении ошибок развертывания логи ДОЛЖНЫ содержать понятную диагностическую информацию
- **FR-009**: Документация ДОЛЖНА описывать процесс развертывания для различных окружений (Linux, WSL, macOS)
- **FR-010**: Система ДОЛЖНА использовать оптимизации Docker (multi-stage builds, layer caching) для ускорения сборки
- **FR-011**: При запуске контейнера web скрипт entrypoint ДОЛЖЕН проверять доступность базы данных перед применением миграций
- **FR-012**: Проблемный enum orders_deliverycompany ДОЛЖЕН корректно мигрировать без ошибок duplicate key

### Key Entities *(include if feature involves data)*

- **Docker Compose конфигурация**: Определяет сервисы (db, redis, web, celery, nginx), их зависимости, health checks, volumes и сети
- **PostgreSQL Database**: Содержит enum типы (orders_deliverycompany и другие), таблицы приложения, должна поддерживать идемпотентные миграции
- **Django Migrations**: Файлы миграций, которые создают/изменяют enum типы и схему базы данных
- **Docker Images**: Образы для каждого сервиса, собираемые из Dockerfile с зависимостями приложения
- **Health Check Scripts**: Скрипты проверки готовности сервисов (pg_isready для PostgreSQL, redis-cli ping для Redis)
- **Entrypoint Scripts**: Скрипты инициализации контейнеров (docker-entrypoint.sh), выполняющие миграции и запуск приложения

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Команда `docker-compose up -d` выполняется успешно в 100% случаев на чистой установке без ошибок в логах
- **SC-002**: Все контейнеры (db, redis, web, celery, nginx) переходят в статус "healthy" или "running" в течение 60 секунд после запуска
- **SC-003**: Миграции применяются без ошибок IntegrityError при первом запуске, повторном запуске и после `docker-compose down`
- **SC-004**: Сборка Docker образов завершается успешно в WSL окружении без SIGBUS ошибок в 100% случаев
- **SC-005**: Время от запуска `docker-compose up` до полной готовности системы (все health checks passed) не превышает 2 минут
- **SC-006**: При повторном применении миграций Django корректно определяет что изменений нет и выводит "No migrations to apply"
- **SC-007**: Документация содержит troubleshooting секцию с решениями для всех известных ошибок развертывания
- **SC-008**: Health checks корректно определяют состояние сервисов - failed health checks приводят к перезапуску контейнера

## Assumptions

- **Assumption 1**: Используется Docker Compose v2.x или выше с поддержкой depends_on с condition: service_healthy
- **Assumption 2**: В WSL выделено достаточно ресурсов для сборки образов (рекомендуется минимум 4GB RAM, 2 CPU)
- **Assumption 3**: Django версии 4.2.13 корректно поддерживает идемпотентные миграции с PostgreSQL enum типами
- **Assumption 4**: Проблема с orders_deliverycompany enum связана с повторным созданием типа в миграциях, а не с данными
- **Assumption 5**: SIGBUS ошибки в WSL вызваны высокой нагрузкой на I/O или память, а не багами в Docker Desktop
- **Assumption 6**: Существующие данные в production базе не требуют миграции (фокус на исправлении процесса развертывания)

## Dependencies

- **Docker Desktop для WSL** должен быть актуальной версии с поддержкой WSL2 backend
- **PostgreSQL** версии используемой в docker-compose должна поддерживать используемые enum операции
- **Django migrations** должны быть корректно написаны с использованием правильных операций для enum типов
- **WSL конфигурация** должна иметь достаточные лимиты памяти и дискового пространства (.wslconfig)

## Out of Scope

- Миграция существующих production данных (фокус только на процессе развертывания)
- Оптимизация производительности приложения (фокус на стабильности запуска)
- Переход на другую СУБД вместо PostgreSQL
- Изменение архитектуры приложения или рефакторинг кода моделей
- Автоматизация деплоя (CI/CD pipeline) - только локальное развертывание
- Поддержка других платформ виртуализации кроме Docker
